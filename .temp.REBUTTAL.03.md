# 4. Retain dual-owned HA, but specify the logical-copy contract precisely

## Two owners and at least three database-specific exchange paths

Keep two three-member Patroni groups with the preferred initial writers in the revised plan.

The selected-table exchange is:

```text
hertzbeat-pg / hertzbeat
    → vector-pg / hertzbeat_replica

vector-pg / lme_vectors
    → hertzbeat-pg / lme_vectors_replica

vector-pg / litellm
    → hertzbeat-pg / litellm_replica
```

The `_replica` database names are **proposed bindings**, not claims about existing databases.

This requires database-specific subscription contracts. PostgreSQL subscriptions connect to a publisher database, and built-in replication matches source and target tables by fully qualified name. A different destination database name is possible; arbitrary automatic schema/table renaming is not the contract. ([PostgreSQL][5])

Keep authoritative databases separate from imported copies. Applications receive read-only access to imports; their migrations must not operate on those copies. Imported rows are neither republished nor promoted as substitutes for physical standbys.

## “Read-only application tables” still require confidentiality review

Preserve the agents’ selected native-table replication design rather than silently reverting to an exchange-only architecture. However, **do not interpret it as permission to copy every HertzBeat or LiteLLM table**.

Bind explicit table/column inventories to the current source schema. Exclude credential material, tokens, sessions, secret-bearing blobs, and unapproved prompt/corpus data by default. Read-only access limits mutation, not disclosure.

Publication membership is not a sufficient security boundary: PostgreSQL does not provide separate publication privileges that make a publication allowlist a complete authorization mechanism. Enforce database, connection, role, and table ownership boundaries. Where those cannot safely separate data, use ordinary source-owned sanitized projection tables or a dedicated exchange database. ([PostgreSQL][6])

## Correct bootstrap and migration ordering

The initial sequence should be:

**DCS and empty HA groups → roles/TLS/endpoints/backups → source schema-only migrations → compatible subscriber schemas → publications/subscriptions and initial synchronization → long-running applications.**

This prevents application startup from racing subscription creation or competing schema migrations.

Replace the `docs_chunks` drop/recreate reset with a reviewed relation-preserving operation. A targeted `DELETE` is a candidate; `TRUNCATE` requires explicit publication and foreign-key analysis. Do not add `CASCADE` or identity resets merely to make the reset succeed.

PostgreSQL logical replication does not carry DDL or advance sequence state. Coordinate HertzBeat, LiteLLM, and vector migrations explicitly, including subscriber-first additive changes where appropriate. ([PostgreSQL][7])

## Test publisher and subscriber failover separately

Preserve PostgreSQL 17 native failover-slot configuration, but require evidence that each eligible standby has the required persistent, synchronized, valid slots, including relevant completed table-sync slots. A configured option is not proof that synchronization occurred. ([PostgreSQL][8])

Also test **subscriber-domain physical failover**: imported data, apply progress, subscription reconnection, and continued application must remain consistent. PostgreSQL’s subscription apply-worker `synchronous_commit` setting is separate and defaults to `off`; explicitly select and test the intended policy instead of assuming application defaults cover it. ([PostgreSQL][9])

Keep `synchronized_standby_slots` role-aware. It names physical slots and waits for the listed standbys; it does not express “any one healthy standby.” An unavailable listed slot can stall logical progress. Safe wait-set changes must coordinate promotion eligibility and synchronized replacement, not simply clear the list. ([PostgreSQL][10])

## Make DCS loss and fencing match the promised behavior

Retain strict synchronous replication with one required standby, and validate actual application session durability settings. Strict mode trades write availability for durability when a safe standby is unavailable. ([Patroni][11])

For the requested **DCS-authority-loss → unavailable** behavior, explicitly keep Patroni `failsafe_mode` disabled in the HA acceptance profile. Failsafe mode can otherwise permit a primary to continue under qualifying DCS-outage conditions. ([Patroni][12])

Test a frozen or failed Patroni process while PostgreSQL remains alive. Removing a proxy route is not sufficient proof of fencing. Use a verified per-domain process fence or exact run-owned guest fence, never physical-host power control. Do not assume two Patroni groups can independently control one watchdog.

Keep `shared-ha` as a separately validated deployment alternative, not a hot toggle on initialized dual-domain storage.

# 7. Define what the availability and replay promises actually prove

## Zero loss: acknowledged PostgreSQL commits

Require **zero missing acknowledged commits in the tested single-lab-failure-domain scenario**.

An independent client witness should record acknowledged transaction IDs and expected values outside the failed domain. Verify those IDs and values after failover. Row counts alone are insufficient.

Track timed-out or connection-lost commits separately as ambiguous outcomes and reconcile idempotently. Do not classify them as successful acknowledgements.

This database target does not establish zero loss after permanent destruction of a local SQLite spool disk.

## Ninety seconds: surviving application clients reconnect to the database

Measure from fault injection to a successful authenticated application database operation through the role-aware endpoint, not merely a healthy Patroni response.

**The proposed topology still contains singleton application stacks.** Losing graph removes its LME services; losing trixie removes HertzBeat/GreptimeDB; losing silmaril removes Malcolm/AI. PostgreSQL HA alone does not make those applications fail over.

Therefore, the 90-second criterion can certify **database reconnection for surviving application clients**. Whole-application recovery requires separately specified and budgeted replicas or relocation. It must not be claimed under the current placement.

Failure exercises affect exact run-owned guests, services, or routes. They do not authorize physical-host shutdown, and guest-loss tests are not physical power-loss certification.

## Five minutes: bounded backlog recovery under continuing arrivals

Retain the five-minute target, but declare backlog size and sustained incoming rate.

For backlog \(B\), arrival rate \(\lambda\), and verified drain rate \(R\), the capacity condition is approximately:

$$
R > \lambda + \frac{B}{300}
$$

A full **4 GiB** backlog requires about **13.65 MiB/s of net catch-up per sink**, before new arrivals and protocol/storage overhead.

At restoration, record a watermark covering all pending obligations. Require those obligations to reach verified readback within 300 seconds while normal arrivals continue. Do not pause producers or shrink the backlog silently to obtain a pass.

Keep independent destination checkpoints, 24-hour retention after complete verification, persistent metric queues, and visible quota backpressure. **Never automatically purge unverified events.**
