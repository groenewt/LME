### 2.4 TLS: enable both certificate-chain and hostname verification

Resolve both reported defects:

**Secure default:** supported deployment profiles must default to verified Elasticsearch TLS.

**Effective verification:** enabling the setting must also enable hostname verification in the consumer’s actual transport implementation.

Python documents that `CERT_REQUIRED` alone does not verify the hostname; `check_hostname` is also required. Elastic likewise advises against disabling certificate verification. ([Python documentation][2])

**Required tests must run through the deployed application client**, not just `curl`:

* A valid chain and matching SAN succeeds.
* A certificate signed by the trusted CA but issued for the wrong hostname fails.

Tailnet encryption is useful transport protection. It is not the closure evidence for a broken application TLS contract.

## 4. Keep dual-owned PostgreSQL HA, with explicit replication and migration semantics

Deploy pinned PostgreSQL 17, Patroni, and compatible pgvector artifacts. Keep two three-member physical HA groups and three DCS voters, with separate Patroni namespaces.

| Domain    | Authoritative databases  | Preferred initial writer | Opposite-domain use                   |
| --------- | ------------------------ | ------------------------ | ------------------------------------- |
| HertzBeat | `hertzbeat`              | `trixie` guest           | Approved application-read-only copies |
| Vector    | `lme_vectors`, `litellm` | `graph` guest            | Approved application-read-only copies |

Application connections always resolve the authoritative domain’s current writer. Logical copies are not substitute failover primaries.

### Publications must preserve ownership and confidentiality

Use explicit per-database publication inventories. Imported relations must not be republished into a loop, and application roles must not write to them.

Refine “read-only application tables” to mean **approved tables and columns**. Inspect HertzBeat and LiteLLM schemas for credentials, tokens, provider secrets, and sensitive configuration before enabling copies. Read-only access does not make copying credentials harmless.

Do not run application auto-migrations against the imported databases. Separate runtime, migration, replication, integration, and backup roles. Keep replication administration away from ordinary application identities.

### State the durability settings and test the real clients

For the HA acceptance profile, require synchronous physical replication with one required standby and strict mode. Verify the effective commit behavior of application and migration connections; do not assume a server default defeats session-level overrides.

Patroni documents that strict synchronous mode blocks writes without a suitable synchronous standby. It also documents limitations, including transactions cancelled while waiting for replication and explicit client overrides. Therefore, “zero loss” must refer to the defined acknowledged-write test, not every possible failure or ambiguous client outcome. ([Patroni][5])

Audit subscription apply workers separately. PostgreSQL 17 gives subscriptions their own `synchronous_commit` setting, defaulting to `off`. For this HA profile, explicitly configure and test the intended subscriber durability, including replicated data and replication-origin progress after subscriber failover. This does not make cross-domain logical exchange synchronous with the publisher’s application transaction. ([PostgreSQL][6])

### Logical-slot continuity needs its own promotion gate

Configure and validate failover-enabled logical slots, physical replication slots, standby slot synchronization, `hot_standby_feedback`, and the necessary replication connection settings.

Before promotion, verify that required logical slots are persistent, synchronized, and not invalidated on the candidate. PostgreSQL documents that slot synchronization is asynchronous, so merely enabling failover is insufficient. ([PostgreSQL][7])

Define how `synchronized_standby_slots` follows eligible candidates. Waiting indefinitely on a lost or invalidated physical slot can stop logical delivery; PostgreSQL explicitly documents that dependency. Do not “repair” it by advancing or dropping slots without reconciliation. ([PostgreSQL][8])

Test both publisher and subscriber failures in both directions, including reconnection, duplicate-safe recovery, row reconciliation, and sustained WAL-pressure alarms.

### Coordinate migrations and vector resets

Replace the `docs_chunks` drop/recreate reset with a relation-preserving operation whose effects on publications, foreign keys, indexes, and application readers are tested. Do not substitute an unexamined `TRUNCATE`; use the selected operation’s explicit replication contract.

Coordinate HertzBeat and LiteLLM schema changes before rollout. PostgreSQL logical replication does not copy DDL or sequence state, so subscriber schemas and any ownership transfer require separate migration work. ([PostgreSQL][9])

Backups must include an isolated restore test and required extension artifacts. A backup stored only on the same failed development resource is not independent recovery evidence.

Validate `shared-ha` on its own fresh deployment. Switching between profiles is a migration decision, not a harmless rerun toggle.

## 6. Preserve delivery and identity guarantees without overstating them

Keep independent destination obligations, original occurrence IDs, typed payloads, timestamps, and canonicalization versions. Verify retrieved content, not merely a sender-supplied hash.

Snapshot destination selection when admitting an event. A profile change must not erase outstanding obligations for previously admitted records.

Retain the **4 GiB log spool, 2 GiB free-disk reserve, 24-hour retention after complete verification, and 256 MiB persistent metric queues per destination**. Declare precisely whether each budget applies per node, relay, or exporter, and include every instance in admission accounting.

Never purge unverified records automatically. Preserve unresolved delivery state during teardown.

### Separate the acknowledgement classes

A synchronous PostgreSQL commit, a local SQLite admission, an HTTP transport response, and a searchable destination record provide different evidence.

A local spool can protect against process restart and recoverable guest outages. It cannot by itself guarantee recovery after permanent destruction of its only storage copy. Consequently, the HA report must identify the failure model for each acknowledgement class.

Where the accepted test preserves disks during a guest outage, demonstrate recovery from those disks. A requirement for admitted-event survival after permanent host-storage loss needs replicated admission or another independently durable retained source; it must not be claimed from local fsync alone.

### Keep the five-minute target measurable

Retain the five-minute retained-event recovery target, but predeclare backlog size, incoming rate, payload distribution, and destination resources.

For backlog \(B\), incoming rate \(\lambda\), and verified drain rate \(\mu\), the idealized drain time is:

$$
T=\frac{B}{\mu-\lambda},\qquad \mu>\lambda.
$$

A full 4 GiB backlog needs approximately **13.7 MiB/s of net verified drain capacity** to clear in five minutes, before additional overhead. Test the declared load envelope rather than an arbitrarily small backlog.

### Keep privileged identity operations narrowly scoped

Preserve Serve-managed HTTPS, owner-restricted proxy sockets, application capabilities, direct automation keys, same-origin checks, 30-second metric collection, 60-second API reconciliation, and 12-hour file-certificate checks.

Update the bootstrap qualification for current Tailscale behavior. Tailscale restricts Serve Unix-socket proxy target configuration to root following TS-2026-005, so that configuration belongs in the declared privileged bootstrap exception, not in an unrestricted rootless workaround. ([Tailscale][12])

Also verify applicable credential-handling fixes before using Tailscale SSH environment forwarding. TS-2026-010 documents historical exposure of forwarded environment values through process arguments and logs, with a fix in 1.102.1 or newer. Keep secrets out of forwarded environment values regardless. ([Tailscale][13])

## 9. Revised execution order and completion rule

**Wave 0: preserve and remediate.** Preserve current work and OCR history; correct the stale blocker reason; reproduce and close secret leakage, consumer dependencies, TLS, profile composition, consumer-profile activation, and gate-status defects using fixtures before real-secret runs.

**Wave 3: deploy collection and applications.** Activate destinations, collectors, monitor reconciliation, durable exports, rootless services, Malcolm’s declared exception, identity proxy, and silmaril AI services.

**Wave 4: prove the system.** Execute positive and negative collection tests, both database profiles, all telemetry selections, browser workflows, fault exercises, reboot, and fresh-overlay repetition.

**Wave 5: reconcile and retain.** Re-run required reviews against the resulting revision, reconcile every finding and outstanding delivery obligation, preserve failure evidence, and perform only verified owned-resource cleanup.

Session-owned credentials are revoked during verified teardown. Reusable bootstrap/provider credentials remain governed by their declared lifecycle. Confirmed exposure requires rotation even when a credential was originally reusable.

Future Atlas/Ranger consumers receive stable resource identities, ownership, dataset lineage, classification, and access-interface contracts. They remain explicitly undeployed and unenforced.

**Completion requires the reported OCR defects to be demonstrably closed, required reviews to have actually returned, and collection, readback, operator workflows, and scoped failure recovery to pass. A corrected note, a bypassed guard, an installed collector, or a skipped probe is not a substitute for any of those results.**
